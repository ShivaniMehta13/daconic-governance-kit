# Plumbed example policies

Example configuration for Daconic 0.3.0, based on `llm_payloaad.txt` supplied by Plumbed. These are proposed PoC rules, not approved organizational policy. Observe and report only; no blocking, external requests, or automatic masking.

## Run

From the repository root, after installing the library:

```sh
python examples/plumbed/demo.py
```

Output contains per-check results and explicit simulation labels. `expected_results.json` records the checked results. Policies can also be loaded by `daconic observe-serve --state ./plumbed-state --policies ./examples/plumbed/policies`; set `DACONIC_API_TOKEN` as described in the main README. Each observation selects one policy ID/version. Installing four policies does not automatically evaluate all four. Submit separate, uniquely identified observations or combine approved checks under a new policy ID before integration.

## Coverage and expected outcomes

| Policy | Scope | Raw fixture | Masked fixture |
|---|---|---|---|
| `plumbed-sensitive-patterns` v1 | Whole outbound JSON, including string-valued logs and prompts; existing PII, credential and payment-card detectors | Violation: email and card-pattern signals | Violation: card-pattern signal only |
| `plumbed-known-field-masking` v1 | 17 named fields in flattened source/target objects must equal the supplied masking placeholders | Violation | Compliant within these fields |
| `plumbed-connection-fields` v1 | Entire `error_trigger_endpoint`, `error_logs`, `rag_response` fields must be omitted | Violation | Violation |
| `plumbed-outbound-binding` v1 | Canonical JSON equality between transformed and outbound captures | Fails if raw is substituted for masked | Passes only in simulated equal-payload case |

The connection example deliberately omits entire fields, including useful troubleshooting context. It is an optional coarse restriction pending Plumbed's decision on permitted connection details. Sanitizing their contents alone does not pass this policy; present null fields also fail. This is not a general public-IP or URL detector and does not stop equivalent content appearing elsewhere. Documentation links remain allowed by this structural rule.

Known-field checks use exact JSON Pointers, including literal commas in keys. Missing or null fields yield UNKNOWN, not compliance. Placeholder equality does not verify how masking was performed, cover arbitrary names/addresses, or cover names/addresses embedded in prompt strings. Email patterns inside strings are scanned by the separate sensitive-patterns profile. The PII category also includes the existing international-phone pattern; it is not a generic name/address model.

## Confirmed detector limitation

The numeric Facebook post ID in `target_api_doc_urls[2]` matches the current Luhn-based card heuristic. It is a known false positive in this sample, not evidence of an actual credit card. Both fixtures therefore fail the card-pattern check. This result is retained rather than suppressing a failure to manufacture a clean demo. A PASS means no configured pattern was detected, not proof of absence of all sensitive information. There is no supplied positive card or secret example; tests inject explicitly synthetic examples separately.

The existing INFRASTRUCTURE detector covers selected private/loopback IP ranges and `.internal`/`.local` hosts. It does not cover this sample's public IP and public service URL. The connection profile uses explicit field restrictions instead.

## Sample provenance and boundaries

- `payloads/raw.json` and `payloads/masked.json` are sanitized derivatives, not byte-identical originals. Service hostname, IP, connection identifiers, record IDs and email values were replaced with demo values. The public IP becomes documentation address `198.51.100.42`; service hostname becomes `connector.example.test`. Public documentation links and structural masking differences are retained.
- The supplied raw example already contains masked emails in its embedded data-object prompt. It is not a completely unprocessed baseline.
- The demo simulates outbound capture for policy evaluation. `present` means the complete simulated outbound value is available, even when its actual content includes masking placeholders. It does not mean the original underlying PII is available.
- The final case marks the actual outbound stage unavailable and returns INSUFFICIENT_EVIDENCE. No provider transmission is established by the supplied file.
- Timestamps and identity metadata are synthetic. No actual model destination, capture time, independent source or transformation version was provided.
- No signed evidence or dashboard state is generated by this offline runner. Use the existing Observer/API with real capture metadata for integration. Runtime/evaluator code is unchanged.
- Source/target ETL mappings are application data, not governance policies. Credentials and card synthetic test values are never sent externally.
